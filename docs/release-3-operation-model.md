# Release 3 Operation Model

## Purpose

This document is the canonical Release 3 design for durable Operations.

Operation is a cross-cutting execution abstraction. It is used by asynchronous managed-container start, stop, restart, and remove Commands and by Session cleanup. It does not belong to the Managed Container domain and must not be reimplemented separately by any feature package.

Resource-specific designs define Command validation, backend effects, and type-specific recovery. They may extend typed input and outcome data, but they must preserve the common ownership, state, admission, recovery, retention, and client boundaries defined here.

## Conceptual boundary

Release 3 uses three conceptual layers:

| Layer | Concepts |
| --- | --- |
| Transport | Request, Response, `request_id` |
| Application | Command, Query |
| Durable execution | Operation created by selected Commands |

One HTTP Request carries one Command or Query. A Query returns an observation directly. A Command either completes synchronously or creates an Operation.

An Operation is created only when accepted work must:

- outlive the originating Request; and
- remain observable and recoverable after daemon restart.

Internal work such as expired-Session cleanup may create an Operation without an originating HTTP Request.

Release 3 durable work includes:

- `container.start`;
- `container.stop`;
- `container.restart`;
- `container.remove`;
- `session.cleanup`.

Queries, synchronous `container.create`, `build`, the existing one-shot `run`, non-interactive exec, and interactive exec are not Operations. `container.create` returns the stopped resource directly. `build`, `run`, and non-interactive exec return one combined bounded `output` synchronously. Interactive exec uses WebSocket transport. None gains durable recovery, persisted output, or replay semantics.

Synchronous process Commands use the existing flat response envelope rather than a nested result object. A started one-shot `run` or non-interactive exec returns HTTP `200` with `ok`, combined `output`, `truncated`, `duration`, and the actual `exit_code`; a non-zero workload exit sets `ok: false` and `code: container_exit_nonzero` without changing the HTTP status. A build failure reported by the backend returns HTTP `422` with `ok: false`, `code: build_failed`, sanitized `message`, combined `output`, `truncated`, and `duration`. Pull follows the same flat bounded-output convention. Transport, authorization, validation, and backend-availability errors retain their normal non-success HTTP statuses.

## Core invariants

Every Operation:

- belongs to exactly one Session;
- records selected asynchronous work, not every Command;
- has a stable public identity distinct from its target resource;
- reaches durable admission only after validation, authorization, and conflict checks succeed;
- survives the Request that created it;
- provides type-specific execution and restart recovery;
- has one immutable terminal status;
- is deleted with its owning Session;
- is working control-plane state, not permanent audit history;
- stores no progress log, stdout/stderr history, or replay stream.

Release 3 has one Operation abstraction. Managed containers and Session cleanup must not introduce separate generic job, task, or queue models. Synchronous Commands must not be wrapped in Operations merely for uniformity.

## Identity and ownership

The common durable model is:

| Field | Meaning |
| --- | --- |
| `operation_id` | Stable public identifier generated by docker-helper. |
| `type` | Operation discriminator. |
| `session_id` | Owning Session. |
| initiator data | Internal Principal, Launcher, administrator, Session, or System attribution used by audit. |
| `target` | Type-specific public target type and identifier. |
| origin request correlation | Internal optional transport correlation; absent for system work. |
| timestamps | Creation, start, cancellation request, and terminal times where applicable. |
| `status` | Durable execution state. |
| terminal outcome | Typed result, normalized error, or cancellation reason. |

Operation belongs to Session, not to the credential that initiated it. Credential rotation or revocation does not rewrite an existing Operation. Current authority over the owning Session determines whether a caller may inspect it.

`initiator` answers who started the work. It is not ownership. Audit events may continue to use `actor`; the two terms belong to different models.

The public Operation representation exposes neither initiator identity nor origin request correlation. Both remain internal audit context. Raw bearer material, secret values, and internal Docker identifiers are never stored in public Operation fields.

An Operation target uses docker-helper public identity. Operation identity must never substitute for ManagedContainerID or Session identity.

## State machine

The public states are:

| Status | Meaning |
| --- | --- |
| `pending` | Admission is complete and durable execution has not started. |
| `running` | Execution started and external effects may exist. |
| `succeeded` | The required result is confirmed. |
| `failed` | Execution stopped without confirming the required result. |
| `canceled` | Execution stopped because internal cancellation was accepted. |

Allowed transitions are:

```text
pending -> running
pending -> canceled
running -> succeeded
running -> failed
running -> canceled
```

Terminal status is immutable. Retry creates new work unless an idempotency record resolves the request to the original Operation.

`failed` and `canceled` do not promise rollback. Partial backend effects are inspected and handled by the Operation type's recovery contract.

Timeout is a normalized error code on `failed`, not a separate status. `cancel_requested_at` is internal control data, not another public state. Release 3 exposes no public `operation cancel` Command.

## Admission and public API

Authentication, authorization, request normalization, and target resolution happen before idempotency lookup. For a supplied `Idempotency-Key`, an existing Session-scoped association is resolved before evaluating current runtime state: an identical replay returns the original Operation even if the target now already satisfies the requested postcondition.

For a fresh request, validation, resource-state checks, and conflict checks finish before an Operation enters `pending`. A start of an already running Managed Container and a stop of an already stopped one return the current container representation with HTTP `200 OK`, create no Operation, and create no idempotency record. Other admission failures are returned as HTTP errors and create no Operation.

A lifecycle Command that requires mutation returns `202 Accepted`, the Operation identity, and its `Location`.

The API exposes:

- lookup by Operation ID;
- bounded listing within the owning Session;
- simple `status`, `type`, and public-target filters.

It exposes no generic progress percentage, log URL, replay cursor, or cancellation URL. A terminal public representation is immutable.

The CLI waits for terminal status by default and may return after admission with `--detach`. A CLI wait timeout stops only local waiting; it does not cancel accepted work.

## Idempotency

The HTTP API may accept an optional `Idempotency-Key` for a Command that creates an Operation.

The key is scoped to the owning Session. Its deduplication record contains a normalized request fingerprint and the resulting Operation ID and is created transactionally with the Operation. For the Release 3 lifecycle surface, the fingerprint is a versioned tuple of Operation type and public target identity; any later non-secret Command option must be added to the normalized tuple explicitly. Internal `session.cleanup` attempts do not use client idempotency keys.

Reuse behavior is:

| Request | Result |
| --- | --- |
| Same key and identical normalized Command | Return the original Operation. |
| Same key and different normalized Command | Return `idempotency_key_reused`. |

Idempotency is a protocol capability. The CLI does not generate, store, expose, or replay idempotency keys and performs no automatic retry of ambiguous mutations. A direct protocol client may use the capability; the CLI may ignore protocol metadata it does not need.

Deduplication records are deleted with their Operation and owning Session.

## Terminal outcome

`status` determines the permitted terminal data:

| Status | Data |
| --- | --- |
| `succeeded` | Optional type-specific `result`. |
| `failed` | Required normalized `error`. |
| `canceled` | Required `cancellation`. |
| `pending`, `running` | No terminal data. |

`error` contains a stable code, a sanitized human message, and code-specific structured details. `cancellation` contains a stable reason and optional reason-specific details.

A generic `retryable` field is not exposed. Safe retry depends on Operation type and current resource state.

An Operation outcome records execution completion; it does not duplicate the current state of its target. Operation never persists workload output, progress logs, or a replay stream.

## Execution and recovery contract

Every Operation type provides separate `Execute` and `Recover` behavior.

- `Execute` handles a `pending` Operation.
- `Recover` handles a `running` Operation found after daemon restart.
- the generic worker never changes `running` back to `pending`;
- the generic worker never decides whether an external action may be repeated;
- a type cannot be registered without both execution and recovery behavior.

The implementation must serialize state transitions so that one Operation is not actively executed by multiple workers at the same time. Exact SQLite claiming, worker concurrency, and restart scanning mechanics belong to the implementation design; they must not weaken the state machine or delegate recovery decisions to the generic worker.

The Release 3 recovery contracts are:

| Type | Recovery rule |
| --- | --- |
| `container.start` | Confirm the running postcondition and continue start only when required. |
| `container.stop` | Confirm the stopped postcondition and continue stop only when required. |
| `container.restart` | Persist an internal `stop` then `start` step and recover by repeating the current idempotent step; never infer completion from timestamps or replay a monolithic backend restart. |
| `container.remove` | Treat absence of the verified backend object as the achieved postcondition. |
| `session.cleanup` | Re-enumerate Session-owned resources and continue deterministic teardown. |

The established Operation ID prefix is `op_` and is retained for the new durable model. The existing internal `build` and `run` discriminators are retired because both Commands become synchronous. There are no persisted Release 2 Operation rows to migrate.

Build and exec have no recovery entries because they are not durable Operations.

## Concurrency and resource serialization

Operation does not provide a hidden user-command queue. Resource-specific domains define which Operations conflict and how conflicts are reported.

For a Managed Container:

- at most one lifecycle mutation is active;
- `active_mutation_operation_id` records the active mutation transactionally;
- a competing lifecycle Command returns HTTP `409 Conflict` and the conflicting Operation ID; the stable error-code name is fixed by the API design;
- the active reference remains durable across daemon restart and is cleared in the same transaction that records terminal status;
- Queries do not take the lifecycle mutation lock;
- exec may run only while lifecycle admission permits it and never blocks teardown.

Detailed container concurrency belongs to `release-3-managed-container-lifecycle.md`. The Managed Container domain defines the persistent relationship between the resource and its active mutation.

## Internal cancellation and Session cleanup

Session teardown has priority over user work but never issues concurrent lifecycle calls against the same Managed Container.

When teardown claims a Session:

1. new Session-authorized Commands are denied;
2. pending user Operations become `canceled` with reason `session_closing`;
3. running Operations receive `cancel_requested_at` and stop only at a type-specific safe point;
4. an external call already in progress may complete, and its terminal result wins if committed first;
5. `session.cleanup` observes actual backend state and continues deterministic teardown.

This is internal coordination for ownership cleanup, not a public cancellation API or deferred user-command queue.

## Retention and audit

Terminal Operations remain attached to their owning Session. Release 3 defines no independent Operation retention period, delete API, archive, output store, or Operation log store.

A successfully closed Session remains for a fixed internal 10-minute observation grace period so authorized management callers can inspect the terminal `session.cleanup` result. `closing` and `cleanup_failed` Sessions are never removed by this timer. Physical Session deletion removes its Operations and idempotency records through foreign-key cascade.

One `session.cleanup` Operation represents exactly one immutable cleanup attempt. A transient failure such as backend unavailability or bounded timeout terminates that Operation as `failed`; the Session remains `closing` and stores the attempt count and `cleanup_retry_at`. When retry is due, the server creates a new `session.cleanup` Operation. An authorized Principal, owning Launcher, or administrator may request an immediate new attempt when none is active. Ownership mismatch and other ambiguous authority failures move the Session to `cleanup_failed` and require administrator action. This Session-owned retry schedule does not add an Operation retry state or a generic retry framework and is not workload reconciliation.

Operation records are working control-plane state. Permanent security history belongs to the structured audit stream.

Audit events record Operation ID, Session ID, type, initiator, public target, status transition, error code or cancellation reason, and timestamp. They do not contain bearer material, secret values, workload output, or internal Docker identifiers. Retention and export are controlled through journald policy or external audit storage.

## Thin CLI boundary

The CLI is a lightweight adapter to the public protocol. It may:

- read explicit configuration and credentials;
- validate command-line syntax;
- issue a request;
- wait or poll transiently;
- service an interactive stream;
- render a response and exit code.

It does not persist execution state, implement queues or reconciliation, automatically retry ambiguous mutations, or reproduce server state machines. Explicit configuration and credentials are not execution state.

A protocol capability is not required to have a CLI surface when exposing it would require local workflow state.

## Persistence and compatibility boundary

The common persistence design must support:

- Session ownership and foreign-key cascade;
- immutable Operation identity and type;
- internal initiator attribution and public-target identity;
- durable state transitions and timestamps;
- typed terminal outcome;
- internal cancellation request data;
- versioned type-specific input and recovery data;
- transactional idempotency association;
- resource-specific active mutation references where required.

Exact tables, columns, indexes, worker-claim mechanics, and migration ordering belong to the implementation design.

The implementation must retire the current in-memory build/run Operation API and move both Commands into bounded synchronous request handling. Durable Operation persistence and workers are introduced only for managed-container start, stop, restart, remove, and Session cleanup. Synchronous Managed Container creation owns a separate provisional resource-state recovery contract and is not another generic execution abstraction. Changes to existing states, API fields, configuration, and CLI behavior require an explicit compatibility rule; no persisted Release 2 Operation data exists.

The canonical current-to-target symbol, API, configuration, and test migration is recorded in `release-3-vocabulary-and-implementation-map.md`. Ordered implementation tasks, the target ownership split, dispatcher mechanics, and test gates are defined in `release-3-d0-execution-plan.md`.

## Decisions deferred to implementation designs

The D0 execution plan fixes the implementation ownership and sequence. The following contract details remain to be fixed in their owning designs before the affected executor tasks begin:

- final Release 2.1 Session foreign key and ownership symbols used by the Operation migration;
- type-specific normalized Command input and recovery payloads used for idempotency and restart handling;
- stable HTTP and CLI field names and error details for durable lookup and listing.

Resource-specific Command preconditions, backend calls, and recovery observations are defined in their own detailed designs.

The synchronous Command result shape, terminal HTTP semantics, and output-limit compatibility are fixed by `release-3-d0-execution-plan.md`. Backend-specific D0 tasks must be reconciled with the accepted Docker Engine API boundary before implementation begins.
